# Day 24 — HTTPBin API Testing with Postman

## 📌 Overview

Day 24 focuses on **API functional testing with Postman using HTTPBin**.

The goal of this exercise was to practice testing different HTTP behaviors rather than testing a traditional CRUD application. The collection covers:

* HTTP status codes
* HTTP methods
* Request and response inspection
* Query parameters
* Custom headers
* JSON and form-data payloads
* Cookies
* Redirects
* Response delays
* Streaming responses
* Byte ranges
* UUID generation
* Response headers
* Image and content-type validation
* User-agent and client IP inspection

The collection uses Postman's **environment variables** so that commonly reused values can be changed without modifying individual requests.

---

# 🎯 Objectives

* Practice functional API testing with Postman.
* Understand how different HTTP methods behave.
* Validate HTTP status codes programmatically.
* Validate response bodies and response headers.
* Test query parameters and custom request headers.
* Verify JSON and form-encoded request bodies.
* Test cookie creation, retrieval, and deletion.
* Validate HTTP redirects.
* Practice response-time assertions.
* Test delayed, streamed, and byte-oriented responses.
* Generate and validate UUIDs.
* Extract dynamic response data into Postman environment variables.
* Build a reusable Postman environment for API testing.

# 📂 Collection Structure

The Postman collection is organized around different HTTP/API behaviors.

## 1. Status Codes

The collection tests status-code responses using the environment variable:

```text
{{statusCode}}
```

Requests include:

* `GET Status Code`
* `POST Status Code`
* `PUT Status Code`

Example:

```http
GET {{baseUrl}}/status/{{statusCode}}
```

The tests verify:

* Returned status code matches `statusCode`.
* Response time is below 3000 ms.

This demonstrates how one environment variable can control the expected HTTP status code across multiple requests.

# 🧪 Assertion Strategy

The Postman tests use several types of assertions.

### Status Code

```javascript
pm.response.to.have.status(200);
```

### Environment-Based Status Code

```javascript
pm.response.to.have.status(
    parseInt(pm.environment.get("statusCode"))
);
```

### Response Time

```javascript
pm.expect(pm.response.responseTime).to.be.below(3000);
```

### JSON Property

```javascript
pm.expect(json).to.have.property("url");
```

### Exact JSON Value

```javascript
pm.expect(json.method).to.equal("GET");
```

### Header Validation

```javascript
pm.response.to.have.header("last-modified");
```

### Response Size

```javascript
pm.expect(pm.response.responseSize).to.be.above(0);
```

### Regex Validation

The UUID response is validated using a regular expression to verify its format.

# 🔄 Dynamic Variable Handling

One of the important concepts practiced on Day 24 is extracting runtime data.

The UUID request obtains a value from the API:

```javascript
pm.response.json().uuid
```

and stores it in:

```text
lastUUID
```

using:

```javascript
pm.environment.set("lastUUID", pm.response.json().uuid);
```

This demonstrates the basic pattern:

```text
API Response
     ↓
Extract Value
     ↓
Store Environment Variable
     ↓
Reuse in Later Requests
```

# 🧠 Key QA Concepts Practiced

## 1. Functional API Testing

Verifying that an API returns the expected:

* Status code
* Response body
* Headers
* Data
* HTTP method behavior

## 2. Contract-Oriented Validation

Instead of simply checking whether a request returned `200`, assertions validate specific response properties.

For example:

```text
Status = 200
+
Method = GET
+
URL field exists
```

## 3. Negative/Alternative HTTP Behavior

The collection also exercises behavior such as:

* Redirects
* Delays
* Different HTTP methods
* Empty/non-JSON response bodies
* Image responses
* Streaming responses

## 4. Dynamic Test Data

The UUID example demonstrates how API responses can generate data that is stored and reused through environment variables.

## 5. Performance Awareness

Several requests include response-time assertions such as:

```text
< 3000 ms
```

or:

```text
< 5000 ms
```

while the delay endpoint deliberately verifies a slower response.

# 🏁 Day 24 Outcome

Day 24 expanded API testing beyond conventional CRUD operations.

The exercise focused on understanding how HTTP requests and responses behave at a lower level, including:

```text
HTTP Methods
      ↓
Status Codes
      ↓
Headers
      ↓
Query Parameters
      ↓
Request Bodies
      ↓
Cookies
      ↓
Redirects
      ↓
Response Timing
      ↓
Streaming / Bytes
      ↓
Dynamic Variables
```

The main takeaway is that effective API testing is not limited to checking whether an endpoint returns `200`. A QA engineer should also validate the **response structure, headers, data, HTTP behavior, timing, and edge-case behavior** represented by the API.
